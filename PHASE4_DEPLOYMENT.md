# Phase 4 UI deployment

The current local installation uses `CHAT_REQUIRE_SESSION=false`, with report scope fixed to `DEFAULT_ZID` and `DEFAULT_SHOPNO` in `.env`. No POS login is required in this mode. `QUERY_USE_POS_CONNECTION=true` explicitly uses the existing DB connection for validated read-only report templates; the default remains the dedicated reporting connection. Set these flags back to their defaults when deploying authenticated reporting with a dedicated account.

`AI_GENERATED_SQL=true` enables the current generated-query path. The schema snapshot in `sql_schema.json` contains metadata for all 33 observed tables and 1,194 columns. Gemini receives metadata and writes SQL directly; it receives no database credentials or result rows. `GeneratedSqlValidator` parses a limited SELECT grammar, checks column references, parameterizes literals, and rewrites every table source to apply the configured tenant and available shop column. Password, login, token, card-number and other restricted fields cannot be queried. CTEs, subqueries, UNION, system queries, comments, multiple statements and writes are rejected. The legacy report-plan path remains available by setting `AI_GENERATED_SQL=false`.

The model is `gemini-3.1-flash-lite` with low thinking for SQL correctness (`GEMINI_SQL_THINKING_LEVEL=minimal` can trade reasoning for speed). There is normally one generation call and no extra narrative call. Validated query plans are cached for ten minutes per browser session and scoped to schema, date, filters, tenant, shop and prior context; results are always read fresh from SQL Server. Full-schema provider context caching is attempted when available, with fallback to full-schema requests and a cooldown after failures. Cache metadata is blocked from HTTP and excluded from Git. Repeated report plans avoid AI latency. Initial requests still depend on provider latency and quota.

Generation now retries one timeout or transient provider failure, without retrying quota/authentication failures. If the first SQL fails local validation, the model receives one repair attempt with only the rejected query and a safe validation reason. Restricted SQL still cannot execute, and repair is skipped if the request has already spent 45 seconds. Most requests use one AI call; repair may use two. Schema-cache creation has a five-second timeout. The grammar supports searched CASE expressions, NOT IN/LIKE/BETWEEN, COUNT_BIG and common pure string/numeric functions. No rows or SQL Server error details are sent to the model for repair. Prompt/model versions invalidate old query-plan cache entries.

Common SQL execution errors can also trigger the same single repair allowance: numeric aggregate type errors, missing GROUP BY columns, unknown columns/tables, syntax errors and incompatible expression types. Only an allowlisted error category is returned to the model; raw SQL Server messages and database values are never included. Timeouts, quota failures, connection failures and unknown execution errors do not trigger SQL rewrites. Metadata records whether SQL was repaired.

Quoted result aliases may include spaces, symbols or Bangla labels. Bracket escapes are decoded and re-escaped during SQL reconstruction, so label text cannot become SQL commands. Table/column lookup and sensitive-field restrictions remain enforced.

Stored net amounts on Confirmed invoices are the configured sales definition; Dismissed invoices are excluded. Returns are not separately calculated because observed xtype values are NULL. Other questions may query permitted stored fields and joins, but this does not certify new accounting formulas. Reports use the configured page size (100 by default). Ordered lists provide next-page loading using the stored, validated SQL without another AI call. Pagination is bounded to offset 10,000; explicitly requested TOP results remain limited to their requested count and the row cap. Offset pages can change if database records change between requests.

Follow-ups receive the previous question, SQL, title, date bounds, presentation and column metadata, never result rows. A Bangla/English/Banglish request for a list after a total keeps the previous dataset and period and asks the model for underlying records. New context is included in the query-plan cache key. Next-page requests reuse the saved SQL and filters and rerun API validation and tenant/shop scoping.

After schema changes, refresh the snapshot with `php bin/refresh_sql_schema.php`. Where CLI SQL Server access is unavailable, use a loopback POST to `/test_ai_project/bin/refresh_sql_schema.php` with the `X-Schema-Refresh: 1` header. Run `php tests/generated_sql_test.php` and `php tests/bangla_followup_test.php` alongside the four existing test suites.

The interface is [ui/index.html](ui/index.html). Existing `index.php` already redirects browser requests there. It uses plain CSS and JavaScript modules; there is no build step or framework migration. Chart.js 4.5.1 is served locally from `ui/assets/vendor/chart.umd.min.js` with its license in `ui/assets/vendor/LICENSE.chartjs.md`. Only that bundle and license are needed from `vendor/` in a deployment.

Temporary npm extraction/cache files under `ui/assets/vendor/package/`, `ui/assets/vendor/*.tgz`, and `.npm-phase4-cache/` are ignored and are not runtime inputs. Exclude those paths when packaging the site. Automated cleanup of those generated files was rejected by the workspace approval policy; Apache deny rules have been added to the generated directories.

1. Serve the project under the same origin as `api/chat.php`, with PHP sessions and static `.mjs`, `.css`, and `.js` files enabled. The page's content security policy permits only same-origin scripts and API calls. Apply equivalent access controls if the server does not use Apache `.htaccess`.
2. Integrate the host POS login with `$_SESSION['reporting_identity']`, and configure Gemini, the internal Query API, and the dedicated read-only SQLSRV account as described in `PHASE3_README.md`. Run a worker-capable PHP server so chat can call the internal Query API. The current unverified catalog and business rules keep live reports blocked until they are approved.
3. Open the page in an authenticated browser session. `GET /api/chat.php` supplies the CSRF token, authorized shop list, and bounded conversation history. The UI sends questions, optional date/shop selectors, and follow-ups to that API. The API rechecks scope. Page loading uses the server-held next offset.

The UI displays KPI values and table cells only from verified API fields. Assistant commentary and optional Gemini insights are separate text nodes. The insights call receives only a PHP-verified trend label and is skipped for partial reports; set `REPORT_INSIGHTS_ENABLED=false` to disable it. Tables sort and paginate loaded rows; **Load next data page** retrieves more rows from the server. CSV exports the loaded rows, with spreadsheet formula protection for text cells. **Print / Save PDF** uses the browser print dialog; no server-side PDF dependency is installed. Chart.js is optional at runtime: if unavailable, the table remains usable.

Run `php tests/phase1_test.php`, `php tests/phase2_test.php`, `php tests/phase3_test.php`, and `node tests/phase4_ui_test.mjs`. The UI test mocks the API and DOM and checks rendering data flow, chart configuration, CSV safety, pagination, and script hygiene. Review the UI on mobile, tablet, and desktop browsers before production; no live browser screenshot or MSSQL/Gemini run was available in this workspace.
